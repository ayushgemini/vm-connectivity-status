Overview

The vending machine's firmware brings up either Wi-Fi or 4G LTE (SIMCom A7672S modem) behind one connectivity layer, adds a self-serve first-time setup flow so a machine never needs a laptop in the field, and adds a physical reset path for re-provisioning. This note explains how each piece works technically, lets you step through the actual state and hardware logic yourself, and tracks the one open issue and current status by team.

Technical architecture

Dual connectivity — network abstraction

Wi-Fi and cellular behind one client interface

Depending on what was saved during provisioning, the firmware runs one of two client backends behind a single network interface: WiFiClientSecure over the ESP32's native Wi-Fi stack, or TinyGsmClientSecure talking to the A7672S over UART at 115200 baud via TinyGSM 0.12.0. Every backend call — auth, inventory, order creation, payment status, vend confirmation — goes through the same request-building code; only the socket implementation underneath changes.

Over cellular, the modem exposes up to 10 independent socket ("mux") slots. Two clients sharing a slot get their AT responses and unsolicited result codes cross-attributed — one call looks like it silently succeeds while a concurrent one times out for no visible reason. A persistent session manager keeps the LTE data session (PDP context) alive across requests instead of tearing it down each time, and checks session health with direct AT queries (AT+CGATT, AT+CGACT, AT+CGPADDR) rather than trusting library-cached state, which can go stale after the first secure connection.

First-time provisioning — captive portal

Hotspot, wildcard DNS, live connection test

A new or freshly reset machine boots into an access point (SNVM-XXXXXX) running a DNS server that answers every query with its own IP — the standard captive-portal trick that auto-launches the setup page on most phones the moment they join.

  • The portal scans nearby Wi-Fi networks, sorts by signal strength, and flags which are password-protected; a SIM machine gets an APN field instead.
  • Before anything is saved, the firmware actually attempts the connection with what was entered — a wrong password or APN is caught on the spot, not after the installer has driven off.
  • Confirmed settings (network type, credentials, APN, machine passcode) are written to NVS flash under a dedicated namespace, with keys kept under NVS's 15-character key-length limit.

State machine & display

Explicit states, flicker-free redraws

The kiosk runs as an explicit state machine — idle, authenticating, inventory check, awaiting payment, dispensing, error, and so on — with every transition logged over serial for field debugging. Try it in the simulator below.

Each state change resets a display flag so the TFT redraws exactly once per transition. This replaced an earlier timing-window check that could miss the redraw entirely if a network call happened to take a little longer than expected, which showed up as the screen appearing stuck on a stale message like "Authenticating..." even after the machine had moved on.

Motor & dispense control

Home-switch feedback, cooldown

The dispense motor drives against a physical home switch rather than a fixed timed pulse, so mechanical variance or a partial jam still stops the motor at a known physical position, with a timeout as the hard backstop if the switch is never reached. Try the failure mode in the simulator below.

A cooldown period after each dispense prevents back-to-back activations from a bouncing sensor or a repeated user tap from re-triggering the motor mid-cycle.

Field reset button

GPIO8, 3-second hold, dispense-safe

GPIO8 is read with a debounced hold check: three seconds continuously low clears the NVS provisioning namespace and reboots the machine straight back into the setup flow — no laptop or reflash needed in the field. Try the exact timing in the simulator below.

The hold is ignored outright while a dispense is in progress, so a reset can never leave the motor or relay in an undefined state mid-cycle.

Order & payment flow

WebSocket events + HTTPS REST

A hand detected by the IR sensor (GPIO7) in front of the machine is what starts a transaction: only after that detection does the firmware call the Create Order API. A successful order creation moves the kiosk into inventory check, then awaiting payment, where a QR code is generated for that order.

Payment confirmation then arrives in real time over a WebSocket channel; auth, inventory, and order creation go over HTTPS REST — both share the connectivity layer above, including cellular session reuse.

Timeouts are enforced end-to-end (for example, a bounded payment window), so a dropped connection resolves into a clear on-screen error state instead of the machine hanging indefinitely.

⚠ Open limitation: SIM throughput

Over cellular, data throughput is slower than expected in real-world testing — noticeably more so than the same requests over Wi-Fi. Auth, inventory, and order-creation calls do complete, but round-trip times are inconsistent enough that this isn't ready for production yet.

The exact cause isn't confirmed. The connectivity and session-handling logic above is already built to hold and reuse a session rather than reconnect unnecessarily, so this looks like a signal/hardware factor rather than a firmware one — the antenna is the leading suspect, but the hardware team still needs to verify that against other possibilities (module placement, cabling, SIM/carrier itself) before it's confirmed.
